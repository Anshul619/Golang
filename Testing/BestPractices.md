# Best Practices for Mocks and Testing

| Title                                                                                            | Description                                                                                                                                               |
|--------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Use interfaces for testability and flexibility**                                               | Interfaces support dependency inversion and make it easier to mock behaviors in tests. <br/>- They help decouple implementation from usage.               |
| **Never marshal mocks (or structs embedding mock.Mock)**                                         | Mocks simulate behavior and are not meant to represent real data. <br> - Always replace mocks with real or fake data before marshalling or serialization. |
| **Use [mockgen](https://github.com/uber-go/mock/tree/main/mockgen) to generate interface mocks** | Automatically generate mocks to save time and effort. <br> - Reduces boilerplate code and minimizes human errors when mocking interfaces.                 |
| **Keep mocks focused on behavior, not state**                                                    | Mocks should simulate interactions and responses rather than store data. Avoid adding unnecessary fields or complex logic.                                |
| **Avoid over-mocking**                                                                           | Mock only what you need for a particular test. <br/>- Excessive mocking can make tests brittle and hard to understand.                                    |
| **Test against real implementations where possible**                                             | Integration or system tests should use actual implementations or fakes to ensure correctness beyond unit tests.                                           |
| **Group mock expectations logically**                                                            | Organize expectations clearly for each test case to improve readability and maintainability.                                                              |
| **Use fakes or stubs when behavior is simple**                                                   | For trivial methods, a lightweight fake implementation may be easier to manage than a full mock.                                                          |
| **Keep tests deterministic**                                                                     | Avoid mocks that rely on random data, timestamps, or external state, unless those are controlled within the test environment.                             |
| **Document mock usage in tests**                                                                 | Explain why certain methods are mocked or expected. <br/>- This helps other developers understand the intent and prevents misuse.                         |
| **Verify interactions, not internal logic**                                                      | Focus on ensuring that methods are called as expected rather than testing how a mock is implemented.                                                      |
| **Update mocks when interfaces change**                                                          | Keep mocks in sync with the source interfaces to avoid silent test failures or outdated behaviors.                                                        |
| **Use context-aware mocking when appropriate**                                                   | Where applicable, mocks should handle context values and cancellations properly to reflect realistic execution flows.                                     |
